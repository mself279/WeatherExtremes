Methodology

WeatherExtremes estimates how the occurrence rate of an extreme-event indicator (for example, days with precipitation over 3 inches) varies over time. This page explains the math behind the estimator, the parameters you choose on the run page, and what each chart and number on the result page represents.

1. Input format

The analysis takes a CSV with one row per time step on a regular grid. The Event_Date column holds fractional years (1938.2466 ≈ early April 1938), and one or more 0/1 indicator columns mark whether the extreme event occurred at that step.

For the bundled STL Precipitation example, the grid is daily (≈ 1/365 yr per step), and columns Over3, Over4, Over5, Over6 flag days where precipitation exceeded the corresponding threshold in inches. You select which indicator column to analyze when you create a run.

2. Smoothed occurrence rate (Gaussian KDE)

Treat the dates of the N events as a sample T₁, T₂, …, T_N drawn from an unknown rate function λ(t) (events per year). The Gaussian-kernel estimator at any time t is:

λ̂(t) = (1 / h) · Σᵢ K( (t − Tᵢ) / h ),   K(u) = (1/√(2π)) · exp(−u² / 2)

The bandwidth h (in years) controls how far each event's influence spreads. Small h gives a wiggly curve that tracks individual events closely; large h gives a smooth long-term trend at the cost of obscuring short-term changes. There is no "right" bandwidth — picking one is a bias–variance tradeoff, addressed in section 4 below.

The implementation is fully vectorized over numpy: a single broadcast forms the (grid × events) difference matrix, applies the kernel, and sums along the event axis. This is roughly two orders of magnitude faster than a Python loop on the STL dataset.

3. Boundary bias correction

Near the start and end of the observation window, a non-trivial fraction of the kernel's mass falls outside the data and the estimator under-counts events. The standard remedy is the reflection method: copy the data within 3h of each boundary, mirror it across the boundary, and include those reflected dates when computing λ̂(t). The reflected points are dropped before plotting, so only the original window is shown.

Toggle Bias correction off to see the uncorrected estimator dip near the edges of the window.

4. Bandwidth selection

For a candidate bandwidth h, the cross-validation score is:

M(h) = ∫ λ̂(t)² dt − 2 · Σᵢ λ̂₋ᵢ(Tᵢ)

where λ̂₋ᵢ is the leave-one-out estimator (the contribution of Tᵢ is dropped when evaluating the rate at t = Tᵢ). The first term penalizes wiggly estimators; the second rewards estimators that put high density at the actual events. Lower M(h) is better.

The app searches across a user-specified range ([bandwidth_search_min, bandwidth_search_max]) at the chosen step size, computes M(h) for each, and reports the minimizer along with the full curve. Use this curve to sanity-check your h choice rather than blindly accepting the minimum — the score can be flat or have multiple shallow minima with real datasets.

5. Bootstrap confidence band

To quantify uncertainty in λ̂(t), the app uses a simple nonparametric bootstrap on the event list:

For B iterations (default 100), draw N events with replacement from the original T₁, …, T_N; compute the rate estimate on this bootstrap sample; store the resulting curve. After B iterations, take per-grid-point percentiles (5th, 10th, 25th, 50th, 75th, 90th, 95th) to form pointwise confidence bands.

Two notes. First, this is a pointwise band, not a simultaneous one — the probability that the entire true rate curve lies within the band is smaller than the nominal level. Second, increasing B reduces Monte-Carlo error in the percentile estimates but doesn't shrink the band itself; the band's width comes from the data, not the iteration count.

6. Autocorrelation declustering

Some extreme events arrive in clusters — a single weather system can produce several over-threshold days in a row. Counting each one as an independent event inflates the local rate. Declustering keeps only the first event of each cluster.

The cluster length τ is estimated from the autocorrelation of the indicator series: for each lag l from 1 to 14, the integer τ_l = max(0, ⌊−1 / log ρ_l⌋) is computed (where ρ_l is the lag-l correlation), and unique values are used as candidate cluster lengths. Set decluster_tau to a positive integer to enable; 0 disables it. For independent events (e.g., billion-dollar disasters spaced months apart), declustering is unnecessary.

7. Multi-threshold comparison

On the run form, you can pick one primary indicator column plus any number of additional ones. The pipeline computes the rate for each at the chosen bandwidth and overlays them on a single chart, which is useful for visualizing how rare-event frequency changes with the threshold — e.g., 4-inch days versus 3-inch days against the same trend.

9. Outputs reference

Summary metrics

Events analyzed
Number of unique event dates in the chosen indicator column within the observation window (after declustering, if enabled).
Mean rate (events/yr)
Time average of λ̂(t) across the window. A coarse summary — with non-stationary data, the rate at any single year can differ substantially.
Peak year and peak rate
The year (and value) at which λ̂(t) is maximized.
Suggested bandwidth (yr)
Bandwidth that minimizes the cross-validation score in section 4. This is a recommendation, not a constraint — your bandwidth_years choice is what's actually used to draw the rate curve.

Charts

Occurrence rate by bandwidth
Smoothed rate curves at several bandwidths (your chosen bandwidth_years plus 10/15/20/25-yr references), with the events themselves shown as red marks on the x-axis. Shows how sensitive the estimate is to bandwidth choice.
Bootstrap confidence band
The point estimate at bandwidth_years, plus 80% and 90% bootstrap percentile bands. The band widens where the data are sparser (rarer events) and narrows where the rate is well-determined.
Bandwidth selection (MISE)
Cross-validation score across the search range. The red ✕ marks the minimum.
Occurrence rate by threshold
(Only when additional indicators are selected.) The same time window analyzed at multiple thresholds, all using bandwidth_years. Useful for comparing how the rate of more-extreme vs less-extreme events trends together.

10. GHCN data ingestion

Datasets can be created either by uploading a pre-built indicator-column CSV or by importing directly from NOAA's Global Historical Climatology Network — Daily (GHCNd) archive at ncei.noaa.gov/pub/data/ghcn/daily/. The catalog tables (ghcnd-states.txt, ghcnd-stations.txt, ghcnd-inventory.txt) are downloaded once into the local cache by python manage.py sync_ghcn and parsed into the GhcnState, GhcnStation, and GhcnElementAvailability tables. Coverage is restricted to U.S. stations (ID prefix US).

Each 11-character station ID encodes structure: characters 1–2 are the FIPS country code (US, CA, …); character 3 is the network code (W = WBAN airport, C = US Cooperative, 1 = CoCoRaHS, S = SNOTEL, …); the remainder is the network-local ID. So USW00013994 is the WBAN station 00013994 — St. Louis Lambert International Airport.

When you import a station, the per-station daily file (by_station/<ID>.csv.gz) is fetched once into media/ghcn_cache/ and reused on subsequent imports for up to seven days. The transform converts raw GHCN values to display units (PRCP: tenths of mm → inches; TMAX/TMIN: tenths of °C → °F; AWND/WSF2/WSF5: tenths of m/s → mph), drops rows with non-blank quality flags by default, builds a complete daily grid, and applies a user-chosen comparison operator to each candidate threshold to produce 0/1 indicator columns named Over3, Over90, Under0, Over70, etc. The threshold comparison is performed in raw units (e.g. 3 inches → 762 tenths of mm) to avoid float-precision issues at the cutoff.

Imported datasets keep a foreign-key link to the GhcnStation they came from plus a JSON metadata blob capturing element, operator, thresholds (in both display and raw units), date range, observation counts, and quality-filter settings. This provenance is what enables the GEV analysis path described below (which needs the raw daily values, not just the indicator columns).

11. Pre-analysis exploration

The exploration page at /datasets/from-ghcn/<station_id>/explore/ is meant to inform threshold and date-range choices before committing to an analysis run. It generates four diagnostics for any element the station records, all from the same cached daily file:

Data completeness — per-year observation count compared to the expected count (365 or 366), color-coded green / amber / red. Reveals gaps and instrument-changeover artifacts that would otherwise confound trend estimates.

Value distribution — log-scale histogram with vertical lines marking each candidate threshold and the count of events at or beyond each. Helps choose thresholds that produce enough events to be analyzable (rule of thumb: ≥10 across the record) without being trivial (sub-thousand events make smoothing speculative).

Annual extremes — the maximum (or minimum, for elements whose default operator is <) per year, with a linear trend line. This is also the primary input for the GEV analysis described below.

Threshold-crossing frequency — annual count of days that crossed each threshold, stacked by threshold. The poor-man's preview of what the eventual KDE rate curve will show, in raw counts.

A "Use these thresholds in Configure" button forwards the chosen element + operator + threshold list to the import form so exploration flows directly into a configured dataset.

12. GEV analysis (annual extremes)

The kernel-rate analysis (sections 1–7) treats the data as a sequence of discrete event-vs-non-event indicators and asks how the rate of those events changes with time. A complementary question is the magnitude of the worst event each year, and how often a level of a given magnitude occurs. The Generalized Extreme Value (GEV) framework answers that.

For an i.i.d. sequence with finite second moments, the Fisher–Tippett–Gnedenko theorem says the suitably normalized maximum converges in distribution to one of three families — Gumbel, Fréchet, or Weibull — that combine into the three-parameter GEV family with location μ, scale σ > 0, and shape ξ:

F(x; μ, σ, ξ) = exp{ −(1 + ξ(x−μ)/σ)^(−1/ξ) } (ξ ≠ 0)
F(x; μ, σ, 0) = exp{ −exp(−(x−μ)/σ) } (Gumbel limit)

The shape parameter governs the tail behavior. ξ > 0 is the Fréchet regime (heavy tail; no finite upper bound) — typical of precipitation. ξ < 0 is the Weibull regime (bounded above at μ − σ/ξ) — typical of temperature and wind, which have physical limits. ξ ≈ 0 is the Gumbel limit (exponential tail).

Annual block maxima

For each year of record we reduce the daily series of the chosen element to a single value: the maximum (default for PRCP, TMAX, wind) or the minimum (default for TMIN). Years with fewer than min_obs_per_year observations are dropped (an incomplete year's "max" understates the true annual extreme). For minimum-direction analyses, the GEV is fit to −X internally and the location is negated for reporting; scale and shape carry their fitted meaning.

Maximum-likelihood estimation

The fit minimizes the negative log-likelihood

ℓ(μ, σ, ξ) = −n log σ − (1 + 1/ξ) Σᵢ log(1 + ξ y_i) − Σᵢ (1 + ξ y_i)^(−1/ξ)

(where y_i = (M_i − μ)/σ and the support constraint 1 + ξ y_i > 0 applies) over the reparametrized vector (μ, log σ, ξ) using Nelder–Mead. The log-scale parametrization keeps σ strictly positive without bounds. Method-of-moments starting values (Gumbel approximation: σ₀ = std·√6/π, μ₀ = mean − γ·σ₀ with Euler's γ ≈ 0.5772) are robust enough that the optimizer converges on well-behaved climate data in a handful of iterations.

Diagnostics

Empirical vs fitted — annual maxima time series with the fitted percentile lines (10th, 25th, 50th, 75th, 90th, 95th, 99th) overlaid; histogram of the maxima with the fitted GEV PDF curve. Both visualize whether the GEV is a credible model for the data.

Bucket diagnostic — bin the annual maxima into equal fixed-width buckets and compare the observed counts with the GEV-implied expected counts (n · ∫_bin pdf). The default bucket width is element-aware (2°F for temperature, 0.5″ for precipitation, 5 mph for wind) so as not to expose the data's underlying storage discreteness as spurious peaks. We compute both a "full range" diagnostic (covering all observed maxima) and an "upper-tail" diagnostic restricted to the top 25% of the data, which is the part of the distribution most relevant for return-level estimation.

Return levels — the T-year return level is the value x_T such that the annual maximum exceeds it on average once every T years: F(x_T) = 1 − 1/T. By inverting the GEV CDF we read off x_T for T ∈ {2, 5, 10, 25, 50, 100, 200, 500, 1000}. The return-level plot puts T on a log axis and overlays the parametric-bootstrap confidence band.

Reference exceedance — given a reference value x_ref and year (defaulting to the most recent year's observed maximum), report P(X > x_ref) = 1 − F(x_ref) and the corresponding expected return period 1/(1 − F(x_ref)). This is the workbook's "probability of observing a value greater than the 2022 maximum" question generalized.

Confidence intervals: parametric vs nonparametric bootstrap

Two methods, both running by default at 500 iterations.

The parametric bootstrap (Coles 2001, §2.6.5) generates synthetic datasets by drawing 88-year (= n) samples from the fitted GEV(μ̂, σ̂, ξ̂) and refits each. The spread of the refits is the sampling uncertainty under the assumption that the GEV is the correct model. Strengths: smooth, mathematically clean, scales well to small samples. Weaknesses: silently underestimates uncertainty if the GEV is the wrong distribution.

The nonparametric bootstrap (James et al. 2021, §5.2) resamples the observed annual maxima with replacement (some years duplicated, some skipped), refits each. Strengths: makes no distributional assumption; absorbs both sampling and model-misspecification uncertainty. Weaknesses: tail estimates can be jumpy because rare years like 1954's 115°F may be missed in some resamples.

When both methods agree closely, you can quote either. If parametric is much tighter than nonparametric, that gap is the cost of assuming the GEV model. The reverse pattern (nonparametric tighter) shouldn't happen and would be worth investigating. The result page reports both side by side with mean, standard deviation, and 2.5th–97.5th percentile interval per parameter, plus per-method bootstrap parameter histograms.

Why use this alongside the kernel-rate analysis

The two pipelines answer different questions on the same data. The kernel rate is non-stationary and answers "how often did this kind of event happen, and is that frequency changing?". The GEV is stationary (assumes the distribution of annual maxima is constant across the record) and answers "how big is a 100-year event, and how does the observed extreme compare to it?". Used together they triangulate non-stationarity assessments — large gaps between the GEV-implied return level and the kernel-rate trend, or systematic bucket-diagnostic misfit, suggest the underlying distribution is drifting and a non-stationary GEV (with time-varying μ or σ) would be the natural next step.
